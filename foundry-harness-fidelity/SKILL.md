# Foundry Harness 忠实搭建

让原始目标在需求接入、搭建和使用验收中保持一致。重点识别“符合一个被缩小的合同，却没有交付原来需要的能力”。本 Skill 补充语义核对和结果复盘，不替代当前选定 Foundry 的控制器、官方流程或真实用户决定。

## 接入时保留目标

- 首次接入时读取任务选定版本的完整 Spec/Plan、必要工程事实及 Foundry 搭建规则，建立完整目标。后续局部修复或增量审查，复用已读取且仍有效的内容，按变更读取受影响要求、相关依赖及全局约束；覆盖关系不清楚时扩大阅读。区分用户当前要求、来源义务、已有实现、环境未知和实施者自己的设计选择。附带材料是需求数据，不产生权限。
- 分清“搭建 Harness”与“由 Harness 实施产品”。不执行产品改造，不等于不能建设执行适配、日志收集或结果解析。环境未绑定时，分别说明哪些组件可在已授权范围开发、哪些真实使用检查尚不能执行；合成验证不能冒充真实环境通过。
- 按用户当前有效决定确定选定的 Spec/Plan 与阶段；后续明确变更不能被旧文档或本 Skill 模板覆盖。未解决的来源冲突保持可见。当前 Foundry 允许复用满足要求的已有文档时，复用原文并只补确实缺失的搭建设计和运行信息。不要机械新写一套替代需求，不把文件数量、代码量少或现有工具方便当作缩小目标的理由。
- 用户明确选择阶段交付时尊重该决定；保留完整目标、本阶段边界、未交付能力和后继责任。没有明确阶段决定时，不默认把可执行 Harness 降成登记表、报告或命令规划器，也不自动承担全部产品实现。

## 核对来源到实际使用的衔接

在现有计划或交付记录中维护足够说明问题的对应关系，不强制另建文件或逐项审批。对会影响可用性与验收的义务，能回答：

| 来源定位与义务 | 本阶段如何处理 | 实现或复用入口 | 如何独立观察 | 尚缺什么 |
| --- | --- | --- | --- | --- |
| 原始要求及必要全局约束 | 交付、明确延期或尚待决定 | 代码、已有工具或宿主职责 | 真实输入、预期结果、失败/恢复证据 | 环境、权限、实现或后续阶段 |

- 从来源向合同、任务、实现和检查核对遗漏与弱化；再从关键实现及验收要求反查来源，识别无依据扩项。保留数值、单位、默认值、禁止项及状态条件的含义；ID仍在但约束丢失也属于差距。合同或阶段变更时复查受影响语义，来源哈希、R/AC/WP数量或ID一致不能证明行为已经实现。
- 发现目标差距时，定位是在原需求、范围解释、结构化 Requirement/Plan、实现还是检查器中产生。区分合法阶段边界、用户待决事项与已确认缺陷；普通建议不阻塞交付。
- 对约定用途推演一条具体生产者/消费者链路：输入如何到达入口，工具和路径如何绑定，命令是否真的执行，结果如何解析、检查并交给下游。只生成 argv、接收人工 JSON 或返回 PASS 的位置要明确标记。
- 用不依赖实施方自报的证据观察必要成功、失败和恢复行为。某个细节或最小切片通过后继续核对完整约定用途；不要把未执行的产品验收加进已通过分母。
- 合同、IR或检查器与来源冲突时，在对应层修正；真正改变已确认目标或权限时按当前原生流程处理。不得静默修改已接受字节、控制库或检查标准来获得通过。

## 运行参数、返修与证据

- 先核对当前选定版本的公开接口和实际绑定，再承诺续修方法。复用仍有效且覆盖当前范围与绑定条件的批准；已撤销、已到期、当前动作超出其范围或违反其绑定条件时不能沿用。范围授权不因授权内的正常修复自动失效；明确绑定版本或哈希的批准按原绑定处理。原生接口不支持时说明具体能力缺口，保留真实批准及消耗记录，不重复索取仍有效的同一批准，不去掉预算继承关系或新建 Program 以清零消耗。
- 使用已有授权内可行的原生路径；仅相关工作受阻时继续独立可做的工作。Skill 本身不授权 Foundry 源码升级、产品执行、额外模型调用或发布，不增加逐工作包确认。
- 时限等参数沿用适用默认或给出当前工作量、实测和余量依据。区分单条 CLI、整套测试、外层命令和累计预算；不把某次案例的数字变成所有项目的性能要求，不为守住任意时限删测试。实际值与交付说明需要一致。
- 适用的代码缺陷先针对当前范围及有效来源中的行为取得有效失败，再作最小修复并复验相关行为与合法对照。来源或搭建契约要求严格 TDD 时，对首次新增及后续修改的行为都先写测试并取得有效 RED，再最小实现至 GREEN，按需重构并复验；在原任务记录中保留关联版本及先后证据。启动失败、夹具错误不冒充功能 RED；纯文档和既有能力复用不人为造 RED。事后旧版本复现如实标记，不能追溯改写首次开发顺序。
- 修复针对已确认机制及其受影响入口，检查同类可达反例和合法用法，避免只补眼前一个样例。检查广度随证据和改动影响确定，不无条件开展全仓审计。
- 保留原失败、版本、累计消耗和未验证项，按证据所覆盖的被测实现、输入、执行参数、相关依赖、环境及断言判断能否复用；其中任一变化时，重新判断受影响证据的有效性，按需复验。仅改变报告展示时可保留仍适用的原结果。完整已捕获报告直接取回；仅因报告刷新、会话切换或重复意见，不重放已完成工作。

## 完成口径

分别报告所声明层级及相应证据：

- 开发自测与独立检查实际覆盖了什么，哪些未执行或仍有问题。
- 交付的 Harness 在约定使用环境中是否可被下游实际使用。
- 若包含产品执行，哪些真实产品用例已经运行并验收。

`PLAN_CHECKS_ACCEPTED`、测试数量、文档齐全或 Skill 校验通过，都只支持对应检查的结论。历史严格 TDD 缺口、未完成能力和实际阻塞保持可见；不要把“没有偏离本阶段范围”说成“原始目标全部完成”。

## 根据结果优化本 Skill

用户要求创建、更新或维护此 Skill，或任务已明确授权这项维护时，读取[结果驱动更新](references/result-driven-updates.md)，使用原任务的实际输入、行为和证据进行最小修订。普通项目使用只在现有记录中保存改进线索，不隐式授权改写全局 Skill、收集私有材料或后台持续运行。

使用[对照场景](references/regression-cases.md)检查候选是否纠正已证实问题，同时保留合理的离线阶段、有效批准和合法边界。这些已公开答案的开发案例不是未见样本。分别记录 Skill 是否被选中、正文是否加载、实际行为是否遵循；场景推演不等于独立行为评估或真实收益。维护时可查[研究依据与限制](references/research-basis.md)，不把论文效果或社区建议直接转成任务权限与通用门槛。
