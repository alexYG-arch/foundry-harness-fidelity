# Foundry Harness 搭建合同说明

本约定说明 `foundry-harness-fidelity` 如何服务于 **Foundry 的 Harness 搭建合同**：保持用户选定的 Spec/Plan、阶段合同、实现和验收一致，交付能支持约定用途的 Harness。

这里的合同是工程上的范围与验收约定。本文提供通用接入约定和可复用片段，尚未绑定某个具体项目、运行环境、预算或批准。采用时并入项目已有合同或原生记录；不要求另建一套替代 Spec/Plan，也不构成已冻结、已批准的 Start Package。

## 合同对象与职责

| 对象 | 负责什么 |
| --- | --- |
| 用户当前有效决定及选定 Spec/Plan | 确定原始目标、业务约束、当前阶段和明确变更。未解决的来源冲突保持可见。 |
| Harness 搭建合同 | 将目标落实为本阶段交付能力、实现或复用责任、接口与验收方式，并保留延期能力和后继责任。 |
| 本 Skill | 核对遗漏、约束弱化、无依据扩项、无效证据和下游交接缺口；给出有来源的差距判断。 |
| 选定版本的 Foundry 控制器与原生流程 | 管理其规定的状态、冻结、批准、执行绑定、预算、返修及接续。 |
| 实施方与检查方 | 在已授权范围实现或复用能力，提供对应版本与条件的成果和可独立观察的证据。 |

若选定流程使用 Start Package，其候选审阅、批准与后续执行仍走原生入口。文档生成、静态检查或 Skill 校验通过，只支持对应检查结论，不能自行推进受控状态。

## 与 Foundry 现有流程配合

按 Foundry 1.2.2 的[使用指南](https://github.com/alexYG-arch/Harness_Foundry/blob/v1.2.2/docs/USER_GUIDE.md)和[设计指南](https://github.com/alexYG-arch/Harness_Foundry/blob/v1.2.2/docs/HARNESS_DESIGN_GUIDE.md)，接入顺序保持为：

1. 展示版本化搭建文档，确认实际内容与阶段范围；满足要求的已有文档按选定版本政策复用。
2. 基于已确认文档准备 Requirement/Plan、来源和独立检查，沿原有准备入口处理。
3. 展示实际运行 Readback，包括模型和服务、工具、读写域、网络、尝试与时间预算、有效期，记录真实运行批准。
4. 在批准范围内建设、检查、必要修复及交付后使用，恢复时沿原入口取回既有状态和记录。

文档确认解决内容，运行批准解决执行权限；两者充分展示后，一条真实回复可以明确作出两种决定，不能默默相互推断。本 Skill 不增加审批层、Plan 字段、固定阶段或逐工作包确认。选用其他版本时核对其实际入口，不把上述版本说明当作接口兼容性认证。

## 项目接入时需要绑定的信息

以下信息复用项目已有记录；缺失项明确标记为待绑定，不编造路径、命令、预算或批准。

| 绑定项 | 需要写清的内容 |
| --- | --- |
| 来源 | 用户选定的 Spec/Plan、版本或可定位内容、当前有效变更；存在冲突时说明冲突位置。 |
| Foundry | 所选版本或提交、真实可用入口及适用流程；版本限制以该版本接口为准。 |
| 目标与阶段 | 完整目标、本阶段交付、明确延期项、未决项及后继责任。 |
| 工具与环境 | 执行工具、输入输出、工作目录与允许写入范围、依赖和环境状态；区分已绑定与计划使用。 |
| 授权与预算 | 当前动作范围、限制、有效条件、撤销或到期状态；有预算时记录总上限、已用及继承关系。 |
| 交付与验收 | 实现或复用入口、下游使用方式、必要成功/失败/恢复行为、观察方法与证据位置。 |

首次接入需建立完整目标。后续局部修复或增量审查可复用仍有效内容，读取受影响要求、相关依赖和全局约束；覆盖关系不清楚时扩大阅读。

## 交付范围

“搭建 Harness”与“由 Harness 实施产品”分别确定范围。不执行产品业务改造，不能成为遗漏执行适配、日志收集或结果解析的理由：这些能力是否交付，应由有效来源和本阶段约定决定。

来源要求可执行 Harness 时，合同需要说明真实输入如何到达入口、工具和路径如何绑定、命令如何执行、结果如何解析检查，以及下游如何使用。只生成 argv、接收人工 JSON 或声明 PASS 的部分要明确记录其能力边界。

用户明确选择离线规划等较小阶段时，按该阶段交付，并保留完整目标、未交付能力和后继责任。环境尚未绑定时，区分授权内可开发的组件与暂时不能进行的真实使用检查。

项目中维护足够解释重要义务的对应关系即可：

| 来源定位及义务 | 本阶段处理 | 实现或复用入口 | 独立观察方式 | 尚缺条件 |
| --- | --- | --- | --- | --- |
| 原要求及相关全局约束 | 交付、明确延期或未决 | 代码、已有工具或宿主职责 | 真实输入、预期结果、失败/恢复证据 | 环境、权限、实现或后续阶段 |

正向检查遗漏和弱化，反向检查无依据扩项。保留数值、单位、默认值、禁止项和状态条件的含义；编号、数量或哈希一致不能替代行为实现。

## 授权与执行边界

本约定和 Skill 不新增产品执行、Foundry 源码升级、额外模型调用或发布权限，也不增加逐工作包确认。复用仍有效且覆盖当前动作范围与绑定条件的批准；授权内正常修复不使范围批准自动失效，明确绑定版本或哈希的批准继续按原绑定处理。

执行和续修使用当前版本支持的原生路径。接口缺少所需能力时说明具体限制，保留真实批准和累计消耗；不通过改控制库、删除预算继承关系或新建 Program 清零消耗。仅部分工作受阻时，继续独立可做的授权工作。

改变已确认目标或权限时按当前原生流程处理，不静默修改已接受字节、控制库或检查标准以获取通过。

## 验证与验收

适用的缺陷修复针对有效来源中的行为取得有效失败，再最小修复并复验相关行为与合法对照。来源或搭建契约要求严格 TDD 时，首次新增及后续修改的行为都保留测试先行的有效 RED、最小实现后的 GREEN，以及关联版本和顺序证据。启动失败和夹具错误不算功能 RED；纯文档与既有能力复用不人为造 RED；事后复现不能改写首次开发顺序。

证据复用取决于它覆盖的被测实现、输入、执行参数、相关依赖、环境及断言。实际条件变化时判断影响并按需复验；仅改变展示形式时可保留仍适用结果。保留原失败、历史版本、累计消耗和未验证项。

验收分别说明以下层级：

| 层级 | 可以声明的结论 |
| --- | --- |
| 搭建检查 | 开发自测与独立检查实际覆盖的行为、未执行项及仍有的问题。 |
| Harness 使用 | 下游在约定环境中能否用交付目录及声明依赖完成约定用途。 |
| 产品执行 | 仅在范围包含产品执行时，说明已真实运行并验收的具体产品用例。 |

不把“没有偏离本阶段范围”扩大为“原始目标全部完成”，不把未执行的产品验收计入已通过结果。普通优化建议不阻塞交付；实际缺陷、待决事项和合法阶段边界分别报告。

## 适用范围与版本

以上条款解释本仓库 Skill 1.1.2 的接入方式；不声明已完成某个项目的 Foundry 兼容性验证。具体状态名、命令、接受格式和门禁以任务选定的 [Harness Foundry](https://github.com/alexYG-arch/Harness_Foundry) 版本为准。

本仓库提供的 17 个对照场景属于开发材料。结构检查和静态推演可用于发现文档问题，独立行为表现及实际任务收益需以相应执行记录验证。
